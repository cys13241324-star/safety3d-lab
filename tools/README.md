# tools

## harness.js — 게임 로직 시험대

`reigns.html` 의 `<script>` 블록을 그대로 꺼내 **JScript 로 실행**한다.
DOM 을 흉내 내고 좌우 선택 핸들러를 실제로 눌러서, 판이 끝까지 도는지와
밸런스가 어떻게 나오는지를 잰다. Node 없이 Windows 에서 바로 돌아간다.

```
cscript //Nologo tools\harness.js reigns.html 300
```

두 번째 인자는 정책당 판 수(기본 60).

| 정책 | 규칙 |
|---|---|
| triage 100 / 85 / 70 % | **이 판이 보상하려는 플레이.** 규정을 그만큼 알고, 관리비가 닿는 데까지 지킨다. 돈이 모자라면 사람이 죽는 규정(안전손실 14 이상)만 전용해서라도 지키고 나머지는 포기한다 |
| comply always 100 / 85 / 70 % | 아는 만큼 무조건 지킨다. 돈이 없어도 전용해서 지킨다 — FM 대조군 |
| balance the weakest | 카드를 안 읽고 게이지만 본다. 안전·감독이 최저면 준수, 공정·공사비가 최저면 위반 |
| coin flip | 무작위 |
| always left (side-mash) | 늘 왼쪽. 카드를 아예 안 읽는 대조군 |

표의 뒤쪽 세 칸은 이렇게 읽는다.

| 칸 | 뜻 |
|---|---|
| `sheets` | 판당 설명창이 몇 번 떴는가. **모르는 만큼만 올라가야 정상**이다 |
| `need(M)` | 그 판에서 규정대로 하는 데 필요했던 돈의 총액(만원) |
| `divert` | 관리비가 없어 공사비를 전용한 횟수. 되풀이하면 적발되어 감독이 무너진다 |

한 판을 한 줄씩 들여다보려면 `trace` 를 준다. 날짜·게이지 넷·관리비 잔액·
누적 필요액·전용 횟수·그 카드의 조치 비용을 찍는다.

```
cscript //Nologo tools\harness.js reigns.html 1 trace
```

**`always comply` 는 없어졌다.** 좌우를 매 카드 섞기 전에는 「늘 왼쪽」이
곧 「늘 준수」였지만, 섞은 뒤로 그 정책은 동전 던지기와 같아졌다.
이름표만 남아 있어서 한동안 **준수 플레이가 60일 도달 1 %** 로 보였다.
규정을 지키는 사람은 `knows 100%`(`ORA`)로 재야 한다.

세 번째 인자로 `sides` 를 주면 좌우 쏠림만 따로 본다 — 늘 왼쪽·늘 오른쪽·무작위.
셋이 비슷하게 나와야 「카드를 안 읽고 한쪽만 미는」 공략이 죽은 것이다.

```
cscript //Nologo tools\harness.js reigns.html 200 sides
```

`sheets/run` 칸은 **판당 시트(설명창)가 몇 번 떴는지**다. 이 게임은 암기가
목적이지만 매 카드마다 설명창이 뜨면 게임이 아니라 문제집이 되므로,
시트는 틀렸을 때와 사고·보고 카드에서만 뜬다. 그래서 이 숫자는
**모르는 만큼만 올라가야 한다** — 아는 사람일수록 작아야 정상이다.

목표는 **가장 잘한 플레이가 60일 도달률 55~70 %, 무작위 10 % 미만**이다.
「게이지만 보기」가 「아는 사람」을 이기면 그 판은 학습 도구가 아니다.
그리고 **triage 가 comply always 를 이겨야 한다** — 이기지 못하면 이 판은
「무조건 다 지켜라」를 가르치는 것이고, 그것은 자원이 유한한 현장의 일이 아니다.

## sim-balance.py — 게이지 몬테카를로

`reigns.html` 을 파싱해 게이지 네 개의 움직임만 파이썬으로 다시 구현한다.
**2026-09-05 에 들어간 안전보건관리비와 위험 확률 굴림은 모른다.** 부호 설계처럼
게이지만 걸린 문제를 크게 돌려 볼 때만 쓰고, 60일 도달률은 harness 쪽을 믿는다.
돌리면 첫 줄에 그 경고가 찍힌다.

생존 일수 분포·60일 도달률·종료 사유를 내고, 이어하기 저장분이
화면 상태와 일치하는지까지 확인한다.

파일은 **ASCII 로만** 써야 한다. WSH 는 `.js` 를 ANSI 로 읽어서
한글 주석이 들어가면 파싱이 깨진다. 게임 쪽 한글은 ADODB.Stream 으로
UTF-8 로 읽어 eval 하므로 문제없다.

## `data-ok` 시험용 표시

`#card` 에 붙는 `data-ok="l"|"r"` 는 **그 카드에서 규정을 지키는 선택이
좌우 어느 쪽에 섰는지**를 알려 준다. 좌우를 매 카드 섞기 때문에, 시험대가
「규정을 아는 사람」을 흉내 내려면 이 표시가 있어야 한다.

게임 진행에는 쓰이지 않는다. 개발자 도구로 들여다보면 정답을 알 수 있지만,
그렇게까지 해서 이기는 것은 이 게임에서 아무 의미가 없다.

## `artlint.py` — 장면 이름표 검사

```
python tools/artlint.py [reigns.html]
```

`reigns.html` 의 `SC` 안 장면 110장을 훑어 `TX` · `Dh` · `Dv` 이름표를 검사한다.
좌표만 보고 판정하므로 브라우저가 필요 없다. 문제가 있으면 종료코드 1.

1. **판 밖** — 320×132 판을 넘는가. 기준선이 아니라 **글자 상자**(윗머리 9 px ·
   아랫꼬리 2.5 px)로 잰다. 기준선만 보다가 `scaffold` 의 '1.85 m' 윗머리가
   잘리는 것을 놓쳤다.
2. **캡션 자리** — 카드는 그림 좌하단(`left:12 bottom:8`)에 분류 캡션을 자동으로
   붙인다. y 110~128 · x < 150 에 이름표를 두면 그 위에 겹친다. 눈으로는 못 찾는다.
3. **이름표끼리 겹침** — 상자 겹침 넓이가 12 px² 를 넘으면 잡는다.

글자 폭은 monospace 10.5 px 기준 대략치다(한글 9.4 · 그 밖 6.3). 정확한 폭이
아니므로 경계에 걸친 것은 눈으로 한 번 더 본다.

**이 검사는 그림이 맞는지는 보지 않는다.** 축척이 맞는지, 치수선이 실제로 그
규정이 걸리는 두 지점을 잡고 있는지는 사람이 그려 놓고 봐야 안다 —
`docs/reigns/visual.md` ① 장면 감사표가 그 기준이다.

### 축척 검사 (감사 기준 「가」)

이름표에 붙은 길이(`'1.85 m'` · `'90 cm'` · `'12 mm'`)와 치수선의 실제 픽셀 길이로
장면마다 px/m 를 낸다. 한 판 안에서 1.6배 넘게 어긋나면 잡는다.

한 판에 px/m 이 둘이면 셋 중 하나다.
**잘못 그렸거나**(그 자리에서 고친다), **상세원으로 떼야 하거나**(`DET`),
**파단선으로 끊어야 한다**(20 m 를 27 px/m 로는 못 그린다).

`DET(...)` 괄호 안의 치수는 일부러 다른 배율이므로 뺀다 — 상세원을 손으로
그려 두면 검사가 본 판 치수로 세니, 상세는 반드시 `DET` 로 만든다.

## `anchor.py` — 치수선이 무언가를 잡고 있는가 (감사 기준 「나」)

```
python tools/anchor.py [reigns.html]
```

장면에서 **실제로 그려진 좌표를 모두 모은다** — `path` 의 `d` 를 M/L/H/V/C/A 까지
훑고(상대좌표 추적 포함), `R`·`C`·`TANK`·`PG`·`W`/`P` 의 모서리·중심·끝점을 더한다.
그다음 `Dh` 의 두 x, `Dv` 의 두 y 가 그중 하나에 3 px 안으로 닿는지 본다.

닿지 않으면 그 치수선은 **아무것도 재고 있지 않다.** `powerline` 의 3 m 가
전선에도 붐 끝에도 닿지 않은 채 허공에 떠 있던 것이 이 부류다.

처음 돌렸을 때 세 건이 나왔고 오탐은 없었다. 그중 둘은 다른 종류의 잘못이었다 —
**무게(kg)를 세로 치수선에 붙여 놓은 것**. 치수선은 길이를 재는 것이라 애초에
붙일 데가 없었고, 그래서 끝이 허공에 있었다. 지시선과 이름표로 바꿨다.

곡선의 중간점이나 회전한 도형은 좌표로 잡히지 않으므로 오탐이 날 수 있다.
잡힌 것은 보고 판단한다.

### 사람 키 검사

`W`/`P` 글리프의 전체 높이는 **31 단위**다 — 안전모 돔 꼭대기가 −31, 발끝이 0.
판의 px/m 를 알면 그린 사람이 몇 미터인지 역산된다. 1.45~1.95 m 를 벗어나면 잡는다.

배율은 `1.7 × px/m ÷ 31` 로 잡는다. **26 으로 잡으면 사람이 1.19배 커진다** —
실제로 여섯 판이 2.1~2.2 m 짜리 사람을 세우고 있었다.

판의 px/m 이 12~60 밖이면 건너뛴다. 상세 치수(수백 px/m)나 현장 규모 치수(한 자리)
로는 사람 키를 잴 수 없기 때문이다. 이 대역 제한으로 오탐이 26건에서 8건으로 줄었다.

### 6 px 규칙 (visual.md ③ 약속 3)

6 px 미만 치수선은 화살표 두 개가 붙어 버려 읽을 수 없다. 그런 수치는 치수선이
아니라 **지시선이나 상세원(`DET`)** 으로 뺀다. 발끝막이판 10 cm, 워크레스트 3 mm,
안전간극 0.5 mm 가 여기 해당한다.

`DET(...)` 안의 치수는 배율이 다르므로 이 검사에서도 뺀다.

## `onobj.py` — 이름표가 물건 위에 앉았는가 (경고)

```
python tools/onobj.py [reigns.html]
```

`artlint` 는 이름표끼리의 겹침을 잡지만 **이름표 대 도형**은 못 본다. 근로자 다리에,
가연물 상자에, 파이프에 글자가 앉는 것은 그려 놓고 봐야 알던 종류였다.

색이 찬 사각·원·`TANK`·`DRUM`·`DOC`·`W`/`P` 의 범위를 잡아 이름표 상자와 겹치는지
본다. **방 같은 큰 배경면(4000 px² 초과)은 뺀다** — 글자를 얹어도 읽히고, 안 빼면
매번 걸린다.

**종료코드는 항상 0 이다.** 계기판 안의 숫자(`pittemp` 의 '39')처럼 일부러 물건
위에 얹는 이름표가 있으므로 사람이 보고 판단한다. 처음 돌렸을 때 11건 중 7건이
진짜였다.

## lawcheck.py — 인용한 조문이 실재하는가

```
python tools/lawcheck.py [reigns.html]
```

`DECK` 과 `FALLOUT`(사고 카드) 양쪽을 훑는다 — 사고 카드의 열쇠는 `k` 가 아니라
`req` 다. 카드의 `law` 필드에서 조문 번호를 뽑아 법제처 원문
(`../sanup-safety-cbt/build/_laws.json`)과 대조한다. 그 저장소가 나란히 없으면
조용히 건너뛴다.

0. **한 번 걷어낸 값이 되살아났는가** — 있으면 종료코드 1.
   `RETIRED` 목록에 폐지·허구 값을 이름으로 박아 두고 파일 전체를 훑는다.
   조문 대조로는 이걸 못 잡는다 — 그 조문에 없는 값은 수백 개니까.
   실제로 `DECK` 만 고치고 `FALLOUT` 을 빠뜨려 「15 mA」가 살아 있었다.
1. **없는 조문을 인용했는가** — 있으면 종료코드 1.
2. **그림(SC) 이름표의 숫자가 그 조문에 있는가** — 카드의 `f` 만 고치고 그림에 옛
   값이 남는 일이 실제로 열두 군데 있었다. 폐지된 「지게차 0.903 m」와 「항타기
   버팀대 3개」가 그림 안에 그대로 있었다. **그림도 가르치는 면이다.**
   붉은색(`BD`) 이름표는 「지금 어긋나 있는 상태」를 적는 자리라 대조하지 않는다.
3. **`f` 의 `<em>값</em>`이 그 조문 본문에 있는가** — 없으면 목록에 올린다.
   종료코드는 올리지 않는다. 별표·고시·KS 값일 수 있고, 조문이 값을 표(그림)로
   담은 자리(충전전로 접근한계거리표 같은)는 본문에 숫자가 아예 없기 때문이다.
   **눈으로 보라는 목록**이다.

`law` 필드에 「고시」·「별표」·「지침」·「KS」·「GUIDE」·「CODE」·「표준」이 적혀
있으면 그 카드의 숫자는 묻지 않는다. 규칙 밖에서 온 값이라고 이미 밝혔기 때문이다.
**규칙에 없는 값을 쓸 거면 어디서 온 값인지 `law` 에 적는 것이 규칙이다.**

### 왜 만들었나

한 번 훑었더니 **서른 장에서 인용이 어긋나 있었고, 그중 여덟 장은 법령에 아예 없는
수치를 규칙 조문으로 제시**하고 있었다 — 2019·2022·2023년 개정으로 삭제된 값
(지게차 헤드가드 0.903 m, 항타기 버팀대 3개, 잠수 송기량 40 L)이거나, 고시·지침
값을 규칙인 양 적은 것(인력운반 40 %/24 %, 누전차단기 15 mA, 조작부 조도 150 lux,
충전전로 머리 위 30 cm)이었다.

`laws.md` 가 「별표·고시 값은 확인 실패이므로 카드로 만들지 말 것」이라고 못 박아
두었는데도 그랬다. 문서로 세운 원칙은 지켜지지 않는다. 기계에 맡긴다.

## shape.py — 카드 값이 덱의 생성 규칙을 따르는가

```
python tools/shape.py [reigns.html]
```

덱은 두 모양으로만 만들어져 있다(`systems.md` ③).

| | 준수 | 위반 |
|---|---|---|
| **P형** | 안전 + · 공정 **+** · 공사비 **−** · 감독 + | 안전 − · 공정 **−** · 공사비 **+** · 감독 − |
| **B형** | 안전 + · 공정 **−** · 공사비 **+** · 감독 + | 안전 − · 공정 **+** · 공사비 **−** · 감독 − |

즉 **준수는 공정과 공사비 중 하나를 내주고 하나를 얻는다.** 둘 다 내주는 카드를
만들면 그 카드만 유난히 무거워진다. 실제로 안전관리론 세 장을 그렇게 썼더니
판당 여덟 번쯤 뽑히면서 **완주율이 50 → 36 %** 로 내려갔다.
눈으로는 안 보이는 종류의 어긋남이라 기계에 맡긴다.

세 가지를 본다 — 준수가 둘 다 깎는가 / 안전·감독의 부호가 뒤집혔는가 /
위반의 안전 손실이 준수의 이득보다 작은가(어겨도 남는 장사).
법령 카드만 보고, 종료코드는 항상 0 이다.

## hitcheck.py — hit 자리번호가 허공을 가리키지 않는가

```
python tools/hitcheck.py [reigns.html]
```

`hit` 은 「이 카드가 실제로 물은 값」의 `<em>` 자리번호다. `f` 를 고쳐 쓰면서
`<em>` 개수가 줄면 hit 이 허공을 가리키는데, **화면에는 아무 표시도 안 붙을 뿐
오류가 나지 않아** 눈으로는 못 잡는다. 카드 데이터를 손볼 때마다 돌린다.

## deckcov.py — 덱이 기출을 덮는가

`sim-balance.py` 와 `harness.js` 는 판이 **재미있는지**를 잰다. 이것은 판이
**시험에 쓸모 있는지**를 잰다. 밸런스는 서른 번 넘게 쟀는데 커버리지는 한 번도
재지 않고 있었다.

```
python tools/deckcov.py             과목 배분 + 빈출 문턱별 커버율
python tools/deckcov.py --miss 10   빈출인데 덱에 없는 주제 — 다음에 쓸 카드
python tools/deckcov.py --have 15   덱이 덮은 주제 (판정을 눈으로 볼 때)
python tools/deckcov.py --cards     덱 카드별로 무엇을 덮고 있나
```

기준은 `../sanup-safety-cbt/CBT_*/*_CBT.html` 의 `D.cards` 다. 문항마다
`subject`·`mid`(주제)·`fq`(출제빈도)가 이미 붙어 있으므로 **주제를 새로 매기지
않는다.** 24회차 2,880문항에서 고유 주제 1,966개가 나온다.

**전체 커버율은 읽을 것이 못 된다.** 덱 125장으로 1,966주제를 덮는 산술 상한이
6.2 % 다. 볼 것은 `fq` 가 높은 구간의 커버율이고, 그 구간이 낮으면 순서가 뒤집힌
것이다.

한국어 조사를 뗀다. 「강관비계의 구조」와 「강관비계」는 글자가 달라 안 걸리기
때문이다. **두 꼴을 다 담으면 안 된다** — 낱말 수가 늘어 겹침 비율의 분모가
커지면서 점수가 되레 떨어진다(실제로 232 → 216 이 되었다). 바꿔 담아야 한다.
명사 끝에 흔한 글자(도·로·이)는 떼지 않는다. 「안정도」의 도를 떼면 없는 낱말이
생겨 헛걸린다.

거르개이지 증명이 아니다. 「덮었다」는 같은 주제를 다룬 카드가 있다는 뜻이지 그
카드가 기출을 대신한다는 뜻이 아니다. 목록을 눈으로 훑을 것.

## build_focus.py — 빈출 지도를 짓는다

`focus.html` 을 회차와 암기 은행에서 만든다. 손으로 고치지 말고 이것을 다시
돌린다.

```
python tools/build_focus.py
```

**낱말이 아니라 문항 번호로 잇는다.** 주제 이름으로 페이지를 이으려 하면 26 %
밖에 안 붙는데, 문항 번호는 양쪽에 다 있다 — 회차는 `q[].card → cards[].mid` 로,
암기 은행은 `methods[].qs[].src` 에 `2023-3-14` 로. 그 교집합이 2,880 문항
전부라, 주제 → 기출 문항과 주제 → 암기 묶음이 **둘 다 100 %** 붙는다. 이름이
바뀌어도 번호는 안 바뀌므로 잘 버틴다.

3D 실습장만은 손으로 짠 낱말 규칙(`LAB3D`)을 쓴다. 암기 묶음의 `topic3d` 는
묶음 단위라 「기계설비의 위험점 → 지게차」 처럼 엉뚱한 데로 보내고, 그 값 29종
가운데 11종은 실습장에 아예 없는 키다. 실습장 주제가 21개뿐이라 손으로 적는 편이
정확하다.

해설에 실려 오는 인라인 style 도 걷는다(28,226 곳 2.4 MB). 테두리·여백·배경은
페이지 CSS 가 `!important` 로 덮으므로 실어 보낼 까닭이 없다. **`text-align` 만은
남긴다** — center 11,192 · left 12,225 로 섞여 있어 한 값으로 몰면 표가 어그러진다.

## focuscheck.py — 지어낸 빈출 지도가 성한가

`focus.html` 은 3.6 MB 짜리 생성물이라 눈으로 못 본다. 여섯 갈래로 본다.

```
python tools/focuscheck.py
```

① 자료(JSON·가중합·빈도 정렬) ② 해설 태그 1,966개 전수 ③ 링크 세 갈래가 대상에
실재하는가 ④ 걷어야 할 인라인이 남았는가·`text-align` 은 살았는가 ⑤ 스크립트
괄호 ⑥ CSS 덮어쓰기 ⑦ 클래스가 마크업과 CSS 양쪽에 붙어 있는가.

`--deep` 을 주면 ⑧ 이 붙는다. ③ 이 「가리키는 파일이 있는가」까지만 보는 데 비해,
⑧ 은 회차를 열어 **그 번호의 문항이 정말 그 주제인지**를 본다. 2,880개를 다
따라가고 출제빈도도 다시 세어 맞춘다. 24회차를 읽으므로 몇 초 걸린다.

괄호를 셀 때 정규식 리터럴을 먼저 지운다. `esc()` 의 `/[<>&"]/g` 안의 따옴표를
문자열 시작으로 오해하면 그 뒤가 전부 어긋난다. **정상으로 굴러가는 판을 넣어
같은 경고가 나오는지 보는 것**이 이런 오탐을 가리는 가장 빠른 길이다.

## linkcheck.py — 페이지 여섯이 서로 이어지는가

페이지마다 파일 하나로 도는 사이트라 링크가 깨져도 빌드가 알려 주지 않는다.

```
python tools/linkcheck.py
```

① 같은 저장소 링크가 가리키는 파일이 있는가 ② 해시가 대상에 실재하는가

## classcheck.py — 클래스가 마크업과 CSS 양쪽에 붙어 있는가

화면을 못 보는 자리에서 눈 대신 쓴다.

```
python tools/classcheck.py              페이지 일곱
python tools/classcheck.py reigns.html  한 장만
python tools/classcheck.py --dead       안 쓰는 규칙까지 (헛걸림이 많다)
```

**기본은 「쓰는데 규칙이 없다」만 낸다.** 마크업에 적힌 이름과 CSS 에 적힌 이름을
맞대 보면 되므로 탐지가 정확하다.

반대쪽(「규칙만 있고 안 쓴다」)은 `--dead` 로 따로 켠다. 손으로 쓴 페이지는 클래스를
스크립트가 이런저런 방식으로 단다(삼항 · 템플릿 문자열 · 계산된 이름). `reigns.html`
의 `.ok` 와 `.no` 가 그 예다 — 실제로 쓰는데 「안 쓴다」고 걸린다. 지어낸 페이지
(`focus.html`)에서는 양쪽 다 믿을 만하다.

클래스는 세 군데에서 나온다. 마크업, 스크립트가 이어 붙이는 문자열, 그리고 JSON
안에 실려 오는 HTML(거기서는 `class=\"tw\"` 처럼 이스케이프되어 있어 따로 풀어야
한다). 한 군데만 훑으면 멀쩡한 것을 잡는다.

스타일이 아니라 **스크립트 손잡이**로만 쓰는 이름은 뺀다 — `.bTheme` 은 형제
페이지도 규칙 없이 `querySelectorAll` 로만 잡는다. 선택자로 쓰였는지를 보고 가른다.

### 2026-09-07 에 잡힌 것

| 페이지 | 이름 | 무엇인가 |
|---|---|---|
| `index.html` | `sm` | `class="b sm bTheme"` 인데 `.sm` 규칙이 없다 — 작은 단추로 만들려던 것이 안 붙는다 |
| `reigns.html` | `b0` | `class="m b0"` 인데 `.b1`~`.b3` 만 있다. b0 는 기본값이라 규칙이 없는 것이 맞아 보인다 |
| `palace` · `game` | 11개 | 두 파일이 사실상 같아 같은 것이 두 번 잡힌다 |
| `focus.html` | 0개 | 지어낸 파일이라 양쪽 다 0 |

## figs_focus.py · figcheck.py — 빈출 지도의 그림

말로만 적힌 주제 가운데 **그림이라야 잡히는 것**이 있다. 「기계설비의 위험점」은
여섯이 「무엇과 무엇 사이인가」로 갈리는데, 그 「사이」는 글로 읽어서는 안 그려진다.

`figs_focus.py` 가 `주제 이름 → SVG` 를 들고 있고 `build_focus.py` 가 해설 앞에
끼워 넣는다. 없는 주제는 그림 없이 간다.

```
python tools/figcheck.py    좌표가 viewBox 밖인가 · id 가 겹치는가 · 태그가 맞는가
```

### 그리는 규칙

  · viewBox 는 모두 `0 0 120 92`. 같은 크기라야 여럿이 나란히 섰을 때 읽힌다.
  · 기계 부품은 `--line`·`--panel2` — 무대다. **위험점만 `--bad`**, 한 그림에 한 군데.
  · 색은 전부 CSS 변수라 밝은 판에서도 따라 바뀐다.
  · **`<marker>` id 는 그림마다 다르게.** `url(#id)` 는 문서 전체에서 찾으므로 같은
    id 가 여럿이면 첫 번째 것만 붙는다. 모양이 같으면 눈에 안 띄어 더 나쁘다.
